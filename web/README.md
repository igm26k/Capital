# Веб-приложение

React/TypeScript/Vite; версии зафиксированы в package-lock.json. Реализован полный online ручной учет: cookie-вход/регистрация (если разрешена окружением), счета bank/cash/card в шести валютах и архив, expense/income с 1–100 частями, переводы/комиссии/возвраты/корректировки, редакторы и удаление, категории/теги и устройства. История поддерживает серверные фильтры и все страницы; массовая классификация — до 100 подходящих операций одной командой. Все запросы идут к настоящему `/api/v1`.

Основной запуск из корня: `make dev`, сборка: `make web-check`. При доступном Node 24: `npm ci`, `npm run typecheck`, `npm run build` из web/. Деньги преобразуются через BigInt и передаются integer-строками minor units, без float. CSRF хранится только в памяти; cookie HttpOnly/Secure управляется сервером. Пользовательские заметки выводятся React как текст.

Для каждой записи фиксируются UUID ключа, generation и точный JSON. При сетевом/неопределенном результате формы блокируются и предлагается повтор той же команды. Одна неподтвержденная команда сохраняется в sessionStorage текущей вкладки, привязана к пользователю/сессии/workspace и переживает reload; пароль/cookie/CSRF туда не записываются. При смене сессии команда не переносится автоматически. Ошибка generation требует обновления и проверки данных; новый ключ автоматически не создается. Успех подтверждается API, после чего остатки перечитываются. Показанные offline данные могут быть устаревшими, новые offline записи отключены.

Конфликты операций, справочников и массовых пакетов показывают введенную правку рядом с серверными данными; новая версия загружается только по явному действию, финансового auto-resubmit нет. Все страницы счетов/категорий/тегов/устройств читаются через next_cursor. Даты вводятся в browser timezone, неизмененный timestamp/timezone сохраняется буквально, включая микросекунды. Полный persistent outbox и клиентский pull/snapshot mirror относятся к этапу приложений. Финансовые данные незавершенной команды остаются в sessionStorage до подтверждения/смены сессии; это не зашифрованное хранилище.

## Реальная браузерная приемка

Из корня `make e2e` (при необходимости `sg docker -c 'make e2e'`). Требуются Node 24/npm и установленный Google Chrome; иной путь задается `CHROME_PATH`. Скрипт собирает отдельный accounting-test на HTTPS 8444, применяет **только тестовый** compose.e2e.yaml для регистрации, запускает Playwright и останавливает тестовый проект без удаления PostgreSQL volume. Обычные local настройки регистрации не меняются. Не запускайте параллельно другие проверки на accounting-test. Тест добавляет синтетические профили в тестовую БД.

Playwright использует настоящий Chrome/API/PostgreSQL. Инъекция потери ответа выполняется после настоящего route.fetch/commit, затем проверяет точный повтор ключа/body/generation и один расход. Набор из 14 сценариев также проверяет login/logout/revoke, чужой счет, generation/CSRF, offline, split totals, archived assignments, валюты/scales, transfer+fee/refund/date guards и cascade delete, version races/diff, adjustment balance race, atomic bulk и pages/filters. Исторические даты и микросекунды, script-like имена как текст и узкий экран 390px также приняты. Self-signed HTTPS принимается только тестовым браузером; серверный local сертификат проверяется отдельно. Автоматические trace/screenshot отключены, чтобы не сохранять auth credentials в артефактах.

При action_result_expired/idempotency_conflict неподтвержденная команда остается заблокированной до сверки: новый ключ не создается. Автоматическая сверка и управление такими командами относятся к следующему пакету. Данные запоздавшего ответа предыдущей сессии не устанавливаются в новую сессию.

S3-07A: между потерей настоящего ответа и same-key retry тест перезапускает API/web контейнеры **фиксированного accounting-test**, проверяет изменение PID/StartedAt, неизменность PostgreSQL процесса и контрольные SQL измерения. Требуется доступ к Docker из процесса Node (например запуск make через sg docker). В ops/.runtime/e2e/*/vertical-browser.json сохраняются приватные (0600) before/after measurements и allowlist событий API без credentials. Это graceful restart, не проверка аварийного kill или backup/restore.

## Мобильная SPA

Основной интерфейс повторяет Material 3 из Android: нижние разделы «Счета», «Операции», «Еще», карточки счетов, отдельные итоги по валютам, редактор счета и переключатели типа/валюты. Темная тема следует настройке устройства; нижняя панель учитывает safe area. Переходы `#accounts`, `#operations`, `#more` работают без загрузки нового документа, поддерживают прямые ссылки и кнопку браузера «Назад». Переключение разделов сохраняет введенные поля в памяти; перезагрузка страницы сохраняет только неподтвержденную команду, как описано выше. Операции выбранного счета открывают историю с серверным фильтром. Создание операций, переводы и корректировки раскрываются в разделе «Операции»; справочники, отчеты, CSV и устройства — в «Еще».

`npm run test:mobile` запускает отдельный набор Playwright в Chrome с синтетическими ответами API без Docker/БД. Он проверяет мобильную навигацию, фильтры, поля редактора, запрос сохранения, точный повтор неподтвержденной команды после reload, пустое состояние, dark mode и отсутствие горизонтального переполнения на 320/390/768 px. Это проверка браузерного интерфейса и контракта запросов; она не заменяет проверку финансовых изменений на реальном API/PostgreSQL. Скриншоты содержат только синтетические данные и сохраняются в `ops/.runtime/mobile-ui` (вне Git).

## Импорт Wallet

В мобильной SPA откройте «Еще → Импорт из Wallet», выберите `wallet_records.csv`, проверьте переводы, затем подготовьте и подтвердите план. Поддерживается фиксированный формат `wallet_records.csv`: UTF-8/BOM, разделитель `;`, исходные 12 колонок в том же порядке, кавычки и многострочные примечания; до 10 MiB и 20000 строк. Типы «Расход/Доход» и «Expense/Income» задают знак положительного `amount`; суммы считаются через BigInt в валюте `currency`, без округления; `ref_currency_amount` не участвует в расчете списания, зачисления или курса. Счета автоматически находятся по точному имени и валюте, недостающие создаются перед операциями. Ручного выбора счетов и колонок нет. Категории сопоставляются по точному имени или создаются; примечания, исходные категории, метки и способ оплаты сохраняются в описании операции. Исходная выгрузка не добавляется в Git.

Переводы связываются только внутри одного точного времени. Если строк две, это должны быть противоположные движения на разных счетах; в одной валюте суммы должны совпадать. Если строк больше двух, пара принимается только при единственном совпадении с обеих сторон: точная сумма и валюта для одной валюты, точная положительная справочная сумма `ref_currency_amount` для разных валют. Справочные значения сравниваются как десятичные строки без округления. Перевод сохраняет обе исходные суммы и валюты; курс рассчитывает сервер по этим суммам, а не по справочному значению. По соседним временам и датам поиск не выполняется. Неоднозначные и одиночные строки записываются корректировками. Все пары и корректировки видны до подтверждения.

Выгрузка операций не содержит достоверных начальных остатков. Новые счета создаются с нулем и датой самой ранней записи файла; после импорта нужно сверить балансы. При использовании существующих счетов поступающие записи меняют их баланс; учитывайте пересечение уже введенной истории. Повторять можно тот же план с теми же парами переводов. Измененный файл/состав пар не является автоматической сверкой дубликатов между выгрузками.

До первой записи полный план сохраняется в IndexedDB без credentials. Каждый шаг отправляется последовательно через существующий финансовый API со стабильными UUID/key/body. Отдельный небольшой прогресс подтверждается после ответа. После сбоя/потери ответа/перезагрузки пользователь продолжает тот же план; текущая команда повторяется с исходным ключом. Импорт можно приостановить между шагами; уже записанные операции не откатываются. Web Locks защищает от одновременного исполнения в двух вкладках. Смена sync generation останавливает продолжение. Удаление профиля очищает и локальные журналы Wallet. Для следующего файла закройте завершенный импорт.

## Корректирующие проводки Wallet

По уточнению владельца одиночные движения Wallet с `transfer=true` и отсутствующей второй стороной — корректировки. Импорт создает `kind=adjustment`: «Доход» задает положительное изменение остатка, «Расход» — отрицательное. Сохраняются исходные дата, счет, валюта, получатель и примечание; причина указывает на отсутствующий источник/направление. Второго фиктивного счета, категорий расходов и доходов не создается. Все неявные переводы считаются корректировками, в том числе несколько движений с одинаковым временем или суммой.

API `POST /workspaces/{workspace_id}/transactions` принимает `HistoricalAdjustmentCreate`: исходную дату и подписанный ненулевой `amount_minor`. Это прибавление известного движения, а не установка текущего остатка. Команда выполняется с обычными проверками доступа, блокировкой счета, датой открытия, архивом, диапазоном баланса, generation и idempotency. Обычный endpoint сверки текущего остатка не изменен. Изменения финансовой части уже созданной корректировки по-прежнему не допускаются. Схема БД не меняется.

## Единая форма новой операции

В «Операциях» кнопка «+» открывает нативное модальное окно с одним селектом типа: расход, доход, перевод, корректировка. Домашняя кнопка «+» открывает то же окно. Для выбранного типа показывается соответствующая форма с прежними проверками, категориями, частями, тегами и датой; перевод поддерживает две валютные суммы и комиссию, корректировка — фактический остаток и причину. Черновики сохраняются при переключении типа внутри окна. Отмена/Escape закрывают окно без записи; при отправке закрытие блокируется. Неопределенная команда остается в прежнем журнале; отмена окна не удаляет ее, повтор использует тот же ключ и тело. Без нужного количества счетов отправка недоступна, отмена доступна.

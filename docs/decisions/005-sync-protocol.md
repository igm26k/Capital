# 005. Синхронизация: группы, снимки и очередь клиента

Дата: 2026-10-04. Статус: принято для реализации S3-04; S2-04.
Входы: [финансовая модель](003-financial-model.md), [HTTP API](004-api-contract.md), [контракт](../../contracts/openapi.json).

## Гарантии и область

Синхронизируются полные агрегаты account, transaction, category и tag одного пространства. Операции включают entries/allocations/tag_ids. Workspace, профиль, membership, сессии и справочник валют читаются отдельными HTTP API; их права не выводятся из старого снимка. Финансовые клиентские изменения отправляются существующими командами учета, отдельный универсальный push не вводится.

Одно серверное действие создает одну атомарную группу изменений. Группа содержит окончательные представления всех затронутых агрегатов и tombstone удаленных; один агрегат встречается не более одного раза. Перевод, комиссия и три возможных счета не расходятся между страницами. generation_id UUID определяет текущую историю пространства. Sequence — номер группы, а не отдельного события; ordinal=1..group_size задает порядок внутри группы. created_at не используется как порядок commit. Группы разных пользователей одного workspace находятся в общем журнале; action receipts доступны только actor, который отправил команду.

Сервер гарантирует отсутствие второго выполнения зарегистрированного действия в течение жизни пространства при сохраненной истории БД. Восстановление из резервной копии не доказывает сохранность более поздних квитанций: это отдельная граница recovery ниже. Полный исходный ответ доступен 30 дней; после него сохраняется компактная квитанция. Журнал групп хранится минимум 90 дней. Это сроки выбранного протокола, не утверждение о работающей реализации.

## Серверный порядок записи

Таблица `sync_heads`: workspace_id PK, generation_id UUID, last_sequence BIGINT >=0, min_available_sequence BIGINT >=1. Новый workspace начинается с last_sequence=0, min_available_sequence=1. `sync_groups`: workspace_id + generation_id + sequence PK, action_id, actor_user_id (служебный, не публикуется), created_at, change_count, payload_bytes. `sync_changes`: workspace_id + generation_id + sequence + ordinal PK, change_id UNIQUE, entity_type/id, operation, entity_version, payload. Одна группа занимает до 1 MiB сериализованного UTF-8 JSON и до 200 событий. Превышение откатывает действие с 422 sync_group_too_large.

Все пути изменения синхронизируемых данных, включая worker, импорт, массовые правки и административные исправления, используют общий порядок:

1. Получить shared lock users, затем shared lock сессии и повторно проверить credential/expiry/disabled; получить shared lock активного membership. Все последующие блокировки сохраняют этот порядок.
2. Получить `sync_heads` выбранного workspace `FOR UPDATE` до блокировок action, счетов, операций и дерева категорий. Этот mutex действует до commit/rollback.
3. Найти actor-scoped action и проверить хеш/квитанцию/доступ. Повтор готового действия не создает группу. Если квитанции нет, X-Sync-Generation должен совпасть с head.generation_id; иначе 409 sync_generation_conflict без записи action. Затем зарезервировать новое действие.
4. В savepoint проверить версии и выполнить финансовую команду в порядке блокировок модели. Изменения движения увеличивают account.version и balance_version; только категории/теги операции не меняют остаток.
5. После успешной проверки и формирования полных payload назначить N=last_sequence+1, записать группу и события, обновить head и квитанцию; commit делает все видимым вместе. Ошибка int64 sequence => 503, без записи.

Нет `nextval`, номера вне транзакции или номера до захвата mutex. Если A держит mutex, B этого workspace не может получить более поздний номер и завершить commit раньше A. Rollback A возвращает счетчик и данные, следующий успешный writer использует тот же следующий номер. Разные workspace не блокируют друг друга. Один writer на пространство — сознательное начальное ограничение; увеличение пропускной способности требует нового доказательства порядка.

Основание для поведения блокировок — [PostgreSQL: row locks](https://www.postgresql.org/docs/current/explicit-locking.html). Снимок ниже использует READ COMMITTED и явную блокировку head: обычное чтение в этом уровне само по себе не фиксирует один снимок для нескольких запросов ([изоляция](https://www.postgresql.org/docs/current/transaction-iso.html)). Все проверки на реальной PostgreSQL остаются S3-04.

Отзыв membership получает exclusive lock этой membership до изменения доступа; незавершенное действие либо заканчивается до отзыва, либо видит revoked и отклоняется. Нельзя получать head, а затем users/session/membership: порядок должен быть одинаковым для писателей, снимков и очистки. Журнал содержит финансовые payload, поэтому не попадает в обычные логи.

## Pull и курсоры

`GET /workspaces/{workspace_id}/sync/changes?cursor=...&limit=...` возвращает SyncChanges. Cursor непрозрачен для клиента; сервер проверяет подпись, actor, workspace, protocol_version=1, generation_id=G и last_applied_sequence=C. Токен нельзя передавать другому пользователю или workspace. Внутренние поля кодируются канонически и подписываются HMAC-SHA-256; секрет через конфигурацию, не в контракте. Ключи подписи версионируются и сохраняются минимум срок журнала; принудительный отказ старого ключа требует bootstrap. Cursor не содержит финансовые payload.

Некорректная подпись/формат/будущий C>head — 400 cursor_invalid. Неверный actor/workspace — 400 cursor_invalid, без данных исходного пространства. Проверка сессии и membership идет первой. Действующий подписанный cursor другого поколения => 410 cursor_expired. Истекший курсор: C < min_available_sequence-1 => 410 cursor_expired. C=min_available_sequence-1 допустим. Клиент не формирует новый курсор из чисел, начальный resume_cursor получается только из snapshot.

Каждая страница читается в одной REPEATABLE READ транзакции с shared locks users/session/membership и повторной проверкой доступа в этой же транзакции; так head, граница retention и payload принадлежат одному MVCC-состоянию. Возвращаются непрерывные полные группы C+1..K, максимум limit (1–100, default=50), и не больше 4 MiB на сериализованную страницу. Хотя бы первая доступная группа помещается благодаря лимиту 1 MiB. Весь журнал до зафиксированного для страницы head=H доступен; `has_more = K < H`. При отсутствии групп next_cursor означает тот же C, has_more=false. `head_sequence` — H, `min_available_sequence` — актуальная нижняя граница. Новый commit после чтения страницы придет в следующем pull.

`next_cursor` всегда обозначает конец последней полностью возвращенной группы, а не H. Нельзя двигать cursor по MutationResult.sync_group_sequence, ответу ActionOutcome или номеру последнего локального действия: между ними есть чужие действия. Push-ответ применяется по версиям для быстрого отображения, но подтвержденный pull cursor остается прежним.

Клиент сначала проверяет generation_id относительно mirror, затем workspace, возрастающие последовательные номера относительно текущего состояния, полный набор ordinal=1..group_size, уникальность change_id и (entity_type,id), соответствие envelope/payload. В одной локальной транзакции применяет всю страницу к confirmed mirror и сохраняет next_cursor. При crash/ошибке все откатывается; повтор приходит с тем же старым курсором. Payload с меньшей версией не перезаписывает уже полученное более новое состояние; совпавшая версия требует одинаковых данных. Это позволяет принять сохраненный старый push-ответ после более нового pull без потери изменений. Tombstone участвует в сравнении версий; старый upsert не воскрешает удаление.

Счет получает version при любом видимом изменении, поэтому сравнение не ограничивается balance_version. Все ссылки могут применяться в staging внутри транзакции с отложенной проверкой FK: ordinal не требует, чтобы родитель пришел раньше ребенка.

## Bootstrap: согласованный снимок

`POST /sync/snapshots` содержит id UUID; Idempotency-Key обязан совпасть с id. Это read-only materialization, не финансовый action и не группа журнала. В одной READ COMMITTED транзакции сервер проверяет users/session/membership под shared locks, получает head `FOR SHARE`, затем копирует все активные агрегаты и head=N. Shared head не пускает writers до конца копирования; архивация и изменения категорий тоже должны захватывать head. Получается согласованный снимок без удержания DB-транзакции между HTTP-страницами.

Снимок материализуется как immutable JSON-элементы в БД: `sync_snapshots` (actor/workspace/id, generation_id, base_sequence, created_at, expires_at, item_count), `sync_snapshot_items` (snapshot, position, payload). Включаются архивные счета/категории/теги и все неудаленные posted/pending операции; deleted не включаются. Сортировка: category, tag, account, transaction, внутри типа UUID ASC. Максимум 50 000 агрегатов и 64 MiB исходного JSON. Превышение дает 422 snapshot_too_large, не усеченный снимок. На actor/workspace максимум два живых снимка, иначе 429. Больший объем требует отдельного масштабирования перед расширением лимита.

TTL=15 минут с created_at, фиксированная страница <=100 элементов. Snapshot metadata возвращает first_page_token, base_sequence и resume_cursor=N. GET snapshot и GET pages повторно проверяют actor и membership. Page token подписан и привязан к generation/snapshot/actor/workspace/позиции; чужой token/неправильная позиция — 400 cursor_invalid. Повтор страницы возвращает ту же страницу пока snapshot жив. Следующий токен null только на последней странице, в том числе пустого снимка (одна пустая финальная страница).

Истекший snapshot => 410 snapshot_expired. При очистке payload остается компактный маркер actor/workspace/id/expires_at на срок жизни пространства; тот же id не создает другой снимок. Для нового bootstrap нужен новый id. Повтор POST с живым тем же id возвращает ту же metadata и 201. Уникальность actor/workspace/id обеспечивается БД; конкурентные одинаковые POST ждут завершения первой вставки и читают ее результат вместо создания двух снимков. POST с несовпадающим Idempotency-Key отклоняется 400. Неуспешная materialization не создает маркер и может повториться. Потеря ответа POST не делает повтор финансовым действием.

Клиент грузит страницы в отдельный staging mirror, проверяя snapshot_id, workspace, generation_id, base_sequence, уникальность сущностей и суммарный item_count. До получения последней страницы прежний mirror/cursor остается рабочим, outbox не трогается. После последней страницы в одной локальной транзакции заменяет **только confirmed mirror**, сохраняет generation_id и resume_cursor=N и удаляет staging. Старые подтвержденные записи, которых нет в снимке, удаляются из mirror; локальные неподтвержденные действия сохраняются отдельно. Затем pull N+1... получает изменения во время загрузки. Подключение клиента к snapshot не означает подтверждения его outbox.

При истекшей странице staging удаляется, создается новый snapshot с новым id, outbox сохраняется. При отсутствии связи staging можно продолжить пока TTL не прошел. Видимые бюджеты/источники следующих этапов потребуют новых типов, версионирования снимка и схемы.

## Идемпотентность и проверка исхода

`actions` уникальна по workspace_id + actor_user_id + action_id. Квитанция хранит hash, state=applied/rejected, original_http_status, completed_at, response_expires_at, group_sequence и generation_id (только applied), entity_refs и response_body. Полный response_body удаляется через 30 суток, остальные поля остаются до удаления workspace; это исключает повторное выполнение старого ключа после очистки ответов. Никаких секретов и исходного тела запроса в компактной квитанции нет.

Хеш SHA-256 покрывает ASCII-метод, LF, нормализованный API-путь с UUID в нижнем регистре, LF, исходный X-Sync-Generation в нижнем регистре, LF и канонический UTF-8 JSON тела. Ключи объектов сортируются лексикографически по Unicode; порядок массивов сохраняется; пробелы вне строк отсутствуют; числа в этих командах только целые, без дроби/экспоненты; строки сохраняют исходные code points без Unicode-нормализации. Строки используют JSON escapes для кавычки, обратной косой черты, \b, \f, \n, \r, \t; прочие U+0000..U+001F — lowercase \u00xx; остальные символы, включая <>& и U+2028, записываются UTF-8 без escaping. Дубликаты ключей запрещены парсером. Authorization, request_id и CSRF в хеш не входят. Неизвестные query-параметры изменяющей команды отклоняются, чтобы они не меняли ее смысл вне хеша. Разный порядок ключей/пробелы не меняют hash, разный порядок массива и текст меняют. До hash не выполняется trim или нормализация UI, сравнивается полученная команда.

При структурно валидной и авторизованной новой команде terminal domain 409/422 сохраняется как rejected: откат изменений до savepoint, затем запись квитанции ошибки и commit без увеличения head. Повтор возвращает тот же отказ; исправленная команда требует новый action_id. Так старый conflict не начинает неожиданно выполнять операцию после изменения данных.

400, schema validation 422 до регистрации action, 401/403/404 проверки доступа, 413, 429, 500/503 и abort DB не регистрируются как terminal receipt. Они допускают повтор исходной команды. Результат при потере ответа commit неизвестен; клиент проверяет GET actions/{action_id} или повторяет исходную команду с тем же ключом. Авторизация/доступ выполняется перед любым чтением/повтором квитанции; старый успех не обходит отзыв membership.

В течение 30 суток повтор возвращает исходный HTTP-статус и тело, Idempotency-Replayed=true; первое выполнение false. Хеш отличается => 409 idempotency_conflict даже после истечения полного ответа. Хеш совпал, но response_body удален => 409 action_result_expired, без нового движения. GET actions/{id} возвращает ActionOutcome, state, group_sequence и entity_refs, response_body=null. Applied позволяет пометить именно это outbox действие подтвержденным для отправки и обновить mirror pull/snapshot; rejected требует решения конфликта и нового ключа. Чужой actor receipt не виден, 404. Ответ GET 404 означает только отсутствие завершенной квитанции на момент чтения: одновременно отправленная команда еще может commit. Нельзя после 404 сразу создавать новый ключ, нужно повторить прежний.

После receipt applied отображаемый локальный overlay сохраняется до применения группы через pull либо установки snapshot с base_sequence >= group_sequence. Подтверждение отправки само по себе не означает, что snapshot, созданный раньше commit, уже содержит операцию. Overlay снимается атомарно с обновлением соответствующего confirmed mirror; его сохранение не разрешает повтор с новым action_id.

UUID создаваемого агрегата никогда не переиспользуется, включая deleted; если даже новый action пытается создать существующий UUID, он получает domain conflict. Это дополнительная защита, но не замена квитанции.

## Клиентский outbox и конфликты

Android позднее в одной Room-транзакции записывает локальный draft/overlay и immutable outbox: action_id, workspace_id, actor_id, generation_id, method/path, body, base_versions, dependencies, state. Веб первого этапа сохраняет черновик без автономной финансовой очереди. Подтвержденные server payload и локальный overlay хранятся отдельно: новый snapshot не уничтожает draft.

Состояния: queued → sending → applied; sending при потере ответа → uncertain; uncertain повторяет прежний ключ или проверяет квитанцию. Terminal rejected → conflict либо rejected. Неизменяемое тело sending/uncertain не редактируется; следующая локальная правка — зависимое действие. После applied его последователь продолжает с версией подтвержденного агрегата; если еще не отправлялся, может быть окончательно сформирован перед отправкой. Попытка отправленного действия с измененным body запрещена.

Независимые действия допустимы параллельно, финансовые изменения одного агрегата и зависимости отправляются последовательно. Локальное создание счета → расход ссылается на UUID счета; расход отправляется после подтверждения создания. Удаление/возврат/комиссия передают все требуемые версии; никаких last-write-wins для денежных полей. 409 предлагает актуальную серверную запись и черновик, повтор осознанной правки получает новый action_id и актуальные версии.

При cursor_expired отправка outbox приостанавливается, выполняется bootstrap без уничтожения очереди. После установки снимка сначала проверяются sending/uncertain квитанции; applied снимаются с очереди, rejected становятся конфликтами, незарегистрированные повторяются с исходным ключом. Затем queued валидируются против актуального mirror: удаленный исходный расход, архивный счет или измененные base_versions требуют явного разбора. Старый снимок не отменяет уже отправленную команду.

При 401 нужен повторный вход тем же пользователем. Другой пользователь не получает прежний outbox, draft и mirror. При 404 workspace/отзыве membership синхронизация прекращается, cached workspace скрывается; очередь остается изолированной до решения владельца, не отправляется в другое пространство. При удалении workspace его квитанции и журнал удаляются вместе с данными.

## Смена поколения и восстановление БД

При принудительном reset журнала или восстановлении PostgreSQL до возвращения трафика оператор меняет head.generation_id на новый случайный UUID, удаляет старые группы/события этого журнала и задает head=0/min=1. Финансовые таблицы не переименовываются и не получают фиктивных новых версий; новый snapshot устанавливается как полная замена старого mirror. Старые snapshot payload удаляются, их маркеры остаются; запрос живого по старому expires_at снимка возвращает snapshot_expired из-за generation mismatch. Старый подписанный cursor не сравнивается только по sequence и всегда требует bootstrap.

Все ответы MutationResult/SyncChanges/SyncGroup/Snapshot/SnapshotPage и события несут generation_id. Applied receipt хранит исходное поколение, rejected — null. Клиент не сравнивает версии и номера групп между разными поколениями и не применяет задержавшийся старый ответ после установки нового snapshot. Исходный заголовок поколения — часть immutable outbox и hash, не заменяется при автоматическом повторе.

Если old-generation receipt сохранилась, повтор может вернуть исходный исторический ответ, но его payload не смешивается с новым mirror. Исход applied/rejected разбирается по квитанции, а состояние — по новому полному snapshot; для applied старого поколения overlay снимается после установки нового authoritative snapshot без сравнения group_sequence разных поколений. Если старая uncertain команда не имеет квитанции после восстановления, она не переотправляется автоматически в новом поколении: пользователь видит recovery conflict и решает судьбу черновика. Новая осознанная команда получает новый action_id, новое поколение и актуальные версии.

Перед открытием восстановленного окружения все восстановленные sessions отзываются: иначе backup может оживить сессию, отозванную после него. В S6 должны быть доказаны restore с rotation поколения/отзывом сессий, согласованность backup, фактический RPO и процедура разбора неизвестных действий. Этот документ не обещает восстановления данных за пределами выбранного RPO и не считает отсутствующую после restore квитанцию доказательством «никогда не применялось».

## Очистка и граничные случаи

Очистка журнала выполняется под head mutex и удаляет только непрерывный префикс **целых** групп старше 90 суток; граница min_available_sequence обновляется в той же транзакции. Никогда не удаляет отдельный ordinal и не перескакивает более молодую группу. Если журнал пуст, min_available_sequence=head+1 (при head=0 это 1). Clock timestamp не задает sequence; ошибки/сдвиги часов не оправдывают очистку молодой группы. Snapshot и receipt deadlines используют серверное время; на границе now>=expires_at ответ уже истек.

Активный снимок живет 15 минут, поэтому при нормальной retention=90 дней resume_cursor не протухает за время его загрузки. Принудительное административное удаление журнала требует нового bootstrap и отдельной процедуры; оно не считается штатной retention.

| Случай | Результат |
|---|---|
| A получил lock, B пытается записать | B ждет; до commit A его изменений нет; после commit группы идут A затем B |
| A rollback | Нет движения, action и группы; следующий успешный writer использует следующий номер без дырки |
| Повтор неполученного ответа | Исходный key возвращает один и тот же outcome, не создает второй расход |
| Группа перевода больше свободного места страницы | Группа целиком идет на следующую страницу, cursor не прыгает на ее середину |
| Crash после локального применения части страницы | Локальная транзакция откатывает данные и cursor; повтор безопасен |
| Snapshot=N, во время страниц commit N+1 | Снимок остается N, после установки pull возвращает N+1 |
| Cursor ровно перед первой сохраненной группой | Чтение разрешено |
| Cursor старше этой границы | 410 cursor_expired, staging bootstrap сохраняет outbox |
| Applied ответ старше 30 дней | Старый key не выполняется; GET receipt доказывает applied, mirror восстанавливается |
| Два равных расхода с разными action/transaction UUID | Оба сохраняются; совпадение суммы/даты не является дублем |

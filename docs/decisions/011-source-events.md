# 011. Структурированные банковские наблюдения и сверка
Дата2026-10-16. Статус: реализованы intake, явные решения и финансовый apply.

Source event — частный вспомогательный ресурс автора, не новая сущность финансового sync mirror. Intake принимает только структурированные поля без полного уведомления/банковского пароля, проверяет текущую сессию, membership, generation и account/currency. Используются существующие auxiliary receipts с head lock; неизвестные результаты не переиздаются с новым ключом. Состояние intake review не меняет остатки/журнал.

Идентичность события: workspace + actor + package name + hashed external notification identity (migration 0010; первоначальная connection identity остаётся в provenance). Record UUID является handle; другой handle с той же source identity и typed payload возвращает существующий event. Измененный payload дает source_event_conflict; сохраненное наблюдение не перезаписывается. Разные external identities сохраняются даже при одинаковых покупках. Доступ к самому workspace не открывает чужую частную банковскую metadata.

Reconcile сначала использует scoped external ID или явную ссылку на pending ID. Account/currency/kind conflict, удаленная исходная операция, status regression, неоднозначная identity или отмена без связи требуют review. Fuzzy amount/time/merchant не разрешает auto merge даже при единственном кандидате. Возвращаемая ID/version — только предложение: финансовый apply обязан отдельно проверить optimistic version/authorization и сохранить financial receipt атомарно. Пользовательские категории/теги/заметки не входят в банковский patch и не должны перезаписываться.

Реальные банки, провайдер, accounts/permissions и форматы остаются неизвестными. Синтетические unit/integration проверки подтверждают алгоритм и сохранение structured events, а не поддержку банка или работающую синхронизацию с ним.

Дополнение: явное решение записывает immutable session/generation-bound job. Worker использует общий CommandRunner, повторяет тот же action ID/body и атомарно фиксирует transaction_sources + event state + financial receipt/journal. create_pending использует pending delta; confirm_posted меняет только статус, сохраняя entries и пользовательские поля. cancel_pending выполняет обычное soft delete с финансовым tombstone. Metadata link не пишет financial journal. Failed attempt может быть повторена только явным действием после проверки отсутствия applied receipt; старый job/issuer сохраняются в истории. Special unknown/expired outcomes блокируются. Recovery помечает queued как failed/recovery_required и отзывает сессии; незапущенные job не применяются автоматически после восстановления.

Смена шаблона, profile ID или connection ID не создаёт новую запись того же физического уведомления. Hash v2 нормализует время и исключает только идентификаторы provenance; account/amount/currency/direction остаются значимыми. Legacy hash v1 не переписывается, неоднозначные старые записи требуют review. Явная metadata link проверяет направление конкретной проводки и может привязать уведомление к переводу, возврату или комиссии; это не классификация банковским парсером. Подтверждение/отмена через source разрешены только standalone pending expense/income. Они используют текущие суммы и счёт с ожидаемой версией, сохраняя ручные исправления. Интерфейсы показывают исходное наблюдение отдельно от текущих проводок перед действием.

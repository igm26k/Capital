# 004. HTTP-контракт и события

Дата: 2026-10-04. Статус: S2-03 завершена; согласовано с S2-04.
Основание: [модель](003-financial-model.md). Формат выбран по [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html).

## Артефакты и границы

[Основной OpenAPI](../../contracts/openapi.json) — источник HTTP-схем первого этапа, 35 операций (30 S2-03 и 5 S2-04). [Будущий OpenAPI](../../contracts/openapi.future.json) — отдельный предварительный контракт девяти операций бюджетов, отчетов и CSV. Он не означает доступность этих функций на первом этапе. Копии общих схем проверяются на точное совпадение; изменения вносит один владелец. Перед реализацией позднего этапа эти схемы пересматриваются совместно с планом этапа.

[Схема события](../../contracts/events/workspace-change.schema.json) описывает внутренний журнал пространства. [Примеры](../../contracts/fixtures/api-examples.json) служат входами контрактной проверки, не заменяют реальный сервер.

Транспорт синхронизации, снимки, сроки хранения журнала/действий и повторные запросы закреплены в [протоколе S2-04](005-sync-protocol.md). Банковские API, разрешения Android и провайдеры не исследовались.

## Общие правила

Префикс `/api/v1`; JSON UTF-8. Денежные значения, версии и последовательности журнала — строки; UUID — строки. Моменты UTC RFC3339 с Z, исходная зона — IANA. Неизвестные поля запроса отклоняются. Имена и email обрезаются по краям и проверяются на непустое содержимое; заметки не обрезаются. Диапазон денег ограничен regex схемы; переполнение вычисленных сумм и диапазон int64 версий дополнительно проверяются сервисом. Пароль не обрезается и не нормализуется; в MVP email — ASCII, идентичность определяется lowercase всего адреса. JSON с повторяющимися ключами, неверным UTF-8 или несогласованными surrogate escapes отклоняется как bad_request.

Чтение/запись любого workspace требует активного membership. Все вложенные account/category/tag/parent/allocation ссылки проверяются внутри того же workspace. Недоступный чужой UUID возвращает 404, без актуальных версий или иных данных владельца. Каталоги профиля и устройств доступны только текущему пользователю.

Все изменяющие команды учета требуют `Idempotency-Key: UUID`, scoped по actor и workspace. Новая команда также требует `X-Sync-Generation: UUID`, полученный из Workspace.sync_generation_id либо снимка. Несовпадение поколения при отсутствии квитанции отклоняется 409 sync_generation_conflict без регистрации действия. Клиент повторяет неизменные метод, путь и JSON с тем же ключом. Успешный повтор возвращает исходный HTTP-статус и результат, даже если данные позже изменились; для актуального состояния нужен GET. Ключ с другим действием возвращает 409 idempotency_conflict. Повторный запрос также требует действующего доступа. Полный ответ хранится 30 суток; компактная квитанция и hash сохраняются до удаления пространства. По истечении полного ответа старый ключ не выполняет команду повторно: возвращается action_result_expired, исход проверяется через GET actions/{id}.

`MutationResult.sync_group_sequence` обозначает группу действия и не разрешает перескочить pull cursor. `MutationResult` содержит все измененные представления счетов, операций, категорий, тегов и отметки удаления в одном действии. Комиссия и изменения исходного расхода после возврата включаются в результат. GET account/transaction читает версии, остатки и дочерние записи из одного согласованного DB snapshot. GET transaction возвращает один агрегат, а не автоматически весь граф зависимостей; связанные UUID загружаются отдельными GET. `MutationResult.generation_id` проверяется до сравнения версий; старое поколение требует bootstrap. Открывающая операция создается только при создании счета и возвращается в MutationResult, не принимается через POST transactions.

PUT передает полный набор редактируемых полей и ожидаемую версию; отсутствие поля не означает «оставить прежним». Идентификатор, kind, исходный расход возврата и денежная валюта/пара валют операции неизменны. Счет можно поменять только внутри соответствующей валюты. DELETE transaction имеет обязательное JSON-тело; выбранные клиенты и прокси должны поддерживать его, это проверяется при S3-01. Null в `fee` означает удаление существующей комиссии. `expected_fee_version` обязателен и null только при отсутствии комиссии. У expense `expected_parent_version` null для самостоятельного расхода, иначе версия перевода. У refund `expected_transfer_version` null для обычного расхода, иначе версия перевода, связанного с комиссией. Для DELETE `related_versions` содержит версии всех существующих затрагиваемых исходных расходов/переводов/комиссий, исключая основную запись; сервер проверяет полноту, не доверяет клиентскому перечню.

Классификация пакета ограничена 100 уникальными UUID операций. Она полностью заменяет единственную категорию и набор тегов, сохраняя UUID исходной части. Допустимы только неразделенные расходы/доходы без активных возвратов. Комиссию пакетно изменять нельзя: она требует проверки родительского перевода через PUT. Ошибка любой записи откатывает пакет. Редактирование нескольких частей выполняется обычным PUT с проверкой суммы.

Корректировка создается отдельным POST счета, сервер задает occurred_at текущим моментом и проверяет expected_balance_version. Opening и adjustment нельзя удалить; adjustment допускает только правку заметки. Refund не выбирает категорию независимо: она берется из original_allocation_id. При существующих возвратах запрещенные финансовые правки расхода возвращают dependent_transactions.

## Сессии

Сессия — непрозрачный случайный токен минимум 256 бит энтропии; БД сохраняет только его хеш. Регистрация/вход задают `transport`: cookie для веба, bearer для Android. Ответ oneOf не возвращает bearer токен cookie-клиенту. Cookie: `__Host-accounting_session`, Secure, HttpOnly, SameSite=Lax, Path=/; без Domain. API и веб предполагаются на одном origin.

Cookie-изменения требуют X-CSRF-Token, привязанный сервером к сессии, и проверки Origin по разрешенному origin. Токен CSRF возвращается при входе и GET auth/session. Публичные login/register при transport=cookie тоже проверяют Origin, предотвращая подмену входа. Если одновременно переданы cookie и Authorization, запрос отклоняется 400; неоднозначного выбора пользователя нет. Bearer-запросы без cookie не требуют CSRF. Ни финансовые токены, ни Cookie/Authorization, ни тела auth-ответов не логируются.

Idle expiry — 7 дней, absolute expiry — 30 дней с создания. GET auth/session восстанавливает веб после перезагрузки, не создает новую сессию. POST auth/renew продлевает idle expiry до min(now+7 дней, absolute expiry) с тем же credential; автоматического обновления на чтении нет. Истекшая или отозванная сессия не возобновляется, нужен вход. Выход отзывает текущую сессию; отзыв выбранного устройства проверяет владельца. Смена пароля и подтверждение email — отдельное расширение перед публичным выпуском, первый этап не предполагает восстановление пароля.

Пароли: Argon2id v=19, начальные параметры m=65536 KiB, t=3, p=4, уникальная случайная соль 16 байт, выход 32 байта; параметры и соль сохраняются в encoded hash. Основание алгоритма — [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html); эксплуатационную стоимость проверяет S3-03. Сравнение результата constant-time, для неизвестного email выполняется dummy hash с теми же параметрами. Это уменьшает различие работы проверки пароля, но не обещает устранения всех сетевых временных различий. Число параллельных hash ограничивается конфигурацией до запуска публичного сервера.

Финансовые команды и частные чтения проверяют users.disabled_at и сессию под shared locks в порядке users → sessions → memberships → sync_heads. Предварительный lookup credential определяет кандидата user, но не дает доступ до повторной проверки под locks. Операции login/renew/logout/revoke, изменение профиля и disabled_at получают user FOR UPDATE до захвата sessions; они сериализуются между собой и ждут завершения активных защищенных запросов. Revoke возвращает успех после commit; после него новый запрос отозванной сессии отвергается. last_seen_at обновляется отдельно после запроса и не требует повышения shared session lock в середине команды. Disabled пользователь не может продолжать работу через существующие сессии.

Ответы авторизации и частных финансовых API: Cache-Control: no-store. Веб хранит credential только в HttpOnly cookie, CSRF — в памяти. Пользовательский device_name не считается подтвержденным аппаратным идентификатором.

## Пагинация и фильтры

Лимит 1–100, по умолчанию 50. `next_cursor` null завершает выборку; cursor непрозрачен, привязан к пользователю/workspace/фильтрам и не является курсором синхронизации. Некорректный либо неподходящий cursor — 400 bad_request. GET transactions: occurred_at DESC, id DESC; остальные списки — id ASC. Используется keyset pagination; обычные списки не обещают стабильного снимка при параллельных изменениях. Для полной загрузки клиента используется отдельный immutable snapshot протокола S2-04.

Фильтры объединяются AND. from включительно, to исключительно; from < to. category_id совпадает точно, без потомков. tag_id выбирает записи с данным тегом. q ищет подстроку payee/note без учета регистра, не выполняет пользовательский SQL/regex. Архивные счета читаются и участвуют в истории; deleted исключены из списков. Categories/tags/accounts: archived=exclude по умолчанию, include или only явно. Sessions показывает активные собственные сессии; currencies возвращает весь маленький справочник, next_cursor=null.

## Ошибки и лимиты

Ошибка всегда содержит request_id, code, понятный message, field_errors (JSON Pointer относительно тела; `query/...` и `header/...` для прочего ввода), current_versions (только доступные клиенту записи), retry_after_seconds либо null. В field_errors указывается причина конкретного отказа, например insufficient_refundable_amount. Каждая current_versions содержит entity_type, обычную version и balance_version для счета (для остальных сущностей null). На ошибке корректировки field_errors указывает expected_balance_version; version не подменяется версией остатка. Ответ не содержит stack trace и секреты.

| HTTP | Коды и поведение |
|---|---|
| 400 | bad_request/cursor_invalid: JSON, cursor, двойной способ аутентификации |
| 401 | unauthenticated: общий отказ входа, истекшая/отозванная сессия |
| 403 | forbidden/csrf_invalid/registration_disabled: операция не разрешена, Origin/CSRF не совпадает или регистрация выключена |
| 404 | not_found: отсутствующий либо чужой ресурс |
| 409 | version_conflict, idempotency_conflict, dependent_transactions, action_result_expired, sync_generation_conflict |
| 410 | cursor_expired, snapshot_expired: требуется bootstrap или новый snapshot |
| 422 | validation_error, account_archived, amount_out_of_range, no_change, sync_group_too_large, snapshot_too_large |
| 429 | rate_limited; Retry-After и retry_after_seconds совпадают |
| 500 | internal_error; результат записи может быть неизвестен клиенту |
| 503 | service_unavailable; Retry-After при временной недоступности |

Клиент после 409 загружает актуальные данные, сохраняет свой черновик и предлагает осознанную правку с новым ключом. При потере ответа, 500 или 503 повторяет исходный ключ; новый ключ может создать дубль. UI не объявляет успех до подтвержденного ответа. Повтор регистрации существующего email возвращает общий validation_error без поля existing_email, но отличие от успешного 201 раскрывает доступность адреса. Это явно принятая граница локального/тестового этапа: REGISTRATION_ENABLED=false по умолчанию, включение только в локальной/тестовой конфигурации. Публичная регистрация остается закрытой до verification-flow и проверки защиты от enumeration на этапе выпуска. Ограничение попыток входа реализуется по IP и нормализованному email; конкретные эксплуатационные пороги настраиваются в S3-03, контракт не привязывает UI к числу попыток.

Размер тела ручной команды — максимум 256 KiB; превышение возвращает 413 с форматом Error и code=bad_request. Части операции <=100, теги <=50, пакет <=100. Дубликаты UUID частей/строк/ссылок отвергаются сервисом; схема uniqueItems сама по себе не проверяет уникальность одного поля объекта.

## События

Событие несет schema_version=1, change_id, action_id, workspace_id, generation_id, sequence, ordinal, group_size, created_at, operation, entity_type и полный payload `data` или tombstone. Workspace в payload совпадает с конвертом. События приватны для пространства и создаются атомарно с action; не отправляются публичному брокеру. Финансовая операция публикуется агрегатом, entries/allocations отдельно не синхронизируются. Credentials, email и sessions отсутствуют в финансовом журнале.

Account payload имеет version и balance_version. Version увеличивается при любом изменении синхронизируемого представления, включая движения; balance_version — только при финансовых изменениях. Это уточняет модель и позволяет не потерять изменение остатка при одинаковой версии метаданных. Счет публикуется один раз на действие даже при нескольких движениях. Полный порядок, атомарные группы, доставка повторов и bootstrap определены протоколом S2-04; schema sequence сама по себе не доказывает правильность работающего commit.

## Предварительные интерфейсы последующих этапов

Бюджет: категория (null = без категории), валюта, YYYY-MM, положительный лимит; итоги учитывают posted расход/возврат. CRUD ограничен своим workspace и версиями. Одно сочетание категория/валюта/месяц уникально. Семантика дерева категорий уточняется на этапе бюджетов.

Отчет: [from,to), доходы, чистые расходы, категории и точки остатка отдельно по валютам. Частота точек и ограничения диапазона уточняются на этапе отчетов; межвалютного суммирования нет.

CSV: UTF-8, файл до 10 MiB, до 1000 строк в одном атомарном пакете, base64 внутри JSON; mapping задает столбцы, дату, зону, разделители. Это ограниченный первоначальный интерфейс, потоковая загрузка — последующее расширение. Сервис проверяет корректность base64 сверх schema contentEncoding. Preview не меняет остатки, содержит invalid/ambiguous/valid строки и expires_at. Confirm требует версию preview и явные решения для всех неоднозначных строк. link требует transaction_id и expected_transaction_version, create/skip требуют null в этих полях. Невалидная строка может только skip. Автоматический дубль только по надежной идентичности источника; дата и сумма недостаточны. Подтверждение атомарно, после него preview=committed; повтор исходного action возвращает исходный итог. Срок preview уточняется перед этапом CSV.

Экспорт возвращает CSV base64 собственных операций за период, ограничение объема и окончательный формат зафиксирует этап CSV. Это интерфейс данных, не ссылка с неограниченным публичным доступом.

## Граница адаптеров и worker

Будущий адаптер провайдера получает ссылку на credential из защищенного хранилища, external_account_id, cursor и cancellation/deadline. Возвращает структурированные события с устойчивым provider_event_id, external_account_id, исходными суммами/валютами, occurred_at, status и ссылкой на предварительный external_id, а также следующий cursor. Не записывает финансовые таблицы напрямую: импорт идет через общую команду учета/сопоставления с идемпотентностью. Поля могут отсутствовать; неполное событие идет на разбор, не создает выдуманную сумму.

Фоновое задание: id, workspace_id, kind, payload_version, payload, state=queued/running/succeeded/failed, attempt, run_after, lease_until, error_code. Worker берет lease, повторяет с ограниченным backoff и той же идентичностью действия; lease не является гарантией единственного исполнения. В банковском payload нет сырого токена; credential_id разрешается непосредственно перед вызовом. Реализация адаптеров отложена до финального этапа.

## Проверка

Команда `python3 contracts/check_contracts.py` проверяет оба OpenAPI по сохраненной официальной структурной схеме, все $ref, JSON Schema компонентов, параметры путей, обязательные action keys и безопасность cookie-записей, одинаковые общие схемы, допустимые/недопустимые примеры и события. Зависимость указана в contracts/requirements.txt. Денежную арифметику отдельно проверяет `python3 contracts/fixtures/check_financial_model.py`.

Эти проверки не подтверждают работоспособность авторизации, CSRF, PostgreSQL, атомарности и синхронизации; их предстоит проверить на реальных компонентах S3.

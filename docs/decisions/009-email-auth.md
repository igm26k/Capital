# 009. Подтверждение email и восстановление пароля
Дата:2026-10-16. Реализация расширяет ADR004/REV07 без изменения финансового sync.

Production регистрация разрешается только при явном REGISTRATION_ENABLED и AUTH_EMAIL_VERIFICATION, корректном32-byte AUTH_EMAIL_KEY и SMTP с verified TLS. Legacy local/test регистрация201 сохраняется для существующих сценариев. В verification режиме POST auth/register возвращает202 confirmation_required и не создает пользователя/сессию. Ответ и обработка одинаковы для существующих и новых адресов: запрос не делает lookup пользователя. Пароль хешируется Argon2id во всех случаях. Для восстановления запрос содержит только email и всегда ставит одинаковое письмо в очередь для корректного адреса, включая неизвестный.

Код — случайный256-bit base64url, срок30минут. БД сохраняет digest кода; тело исходящего письма защищено AES256-GCM с новым nonce и AAD=challenge UUID. API и worker используют один защищенный ключ, без debug вывода. После успешной доставки cipher удаляется. Worker пытается до5раз с backoff; повтор использует исходный код. Истекшие proofs и письма удаляются не реже maintenance цикла, даже если verification выключен. TTL не обещает мгновенного стирания в резервных копиях.

Per-IP/per-email лимиты и persistent60сек cooldown ограничивают отправку; общий максимум10000живых challenges. Cooldown не заменяет текущий код, ответ остается202. Подтверждение регистрации требует email, код и исходный пароль. Требование пароля исключает подтверждение регистрации, заранее начатой посторонним с известным ему паролем. Неверный/просроченный/использованный код и существующий профиль возвращают общий confirmation_invalid без сессии. Создание user/workspace/session и удаление proof выполняются одной транзакцией; конкурентный код применяется один раз.

Recovery использует отдельный purpose, требует новый пароль12–128символов, атомарно меняет хеш и отзывает все прежние сессии. User→challenge lock order согласован с удалением/авторизацией. Неизвестный адрес нельзя отличить до подтверждения владения mailbox; даже доказав владение, нельзя получить чужую сессию. Сброс пароля не создает новую сессию автоматически. После потери успешного ответа повтор кода может быть отклонен; обычный вход выбранным паролем безопасно восстанавливает доступ. Финансовых команд до подтверждения не создается.

Письмо содержит код для ввода в доверенном клиенте; коды не попадают в URL/Referer. Регистрация устанавливает cookie только после проверки proof и Origin. Native использует bearer transport. Recovery не использует старую сессию как доказательство. Все публичные endpoints имеют rate limits, строгие JSON-поля и no-store. Переносимость между API процессами обеспечивается PostgreSQL.

SMTP поддерживает implicit TLS либо обязательный STARTTLS, проверку hostname/system roots и TLS1.2+. Не предлагающий STARTTLS сервер отвергается, plaintext fallback отсутствует. Delivery ошибки редактируются до общей технической причины. Реальная доставка конкретным провайдером, его credentials/DNS/SPF/DKIM/лимиты проверяются в production; локальные transport tests не являются доказательством доставки внешним получателям.

Удаление профиля стирает его challenges/mail. Восстановленная БД до открытия трафика также стирает все email proofs, чтобы backup не оживлял старые коды. Экспорт данных не раскрывает password hashes, токены или queue ciphertext. Метрики очереди содержат только количества/возраст.

# Этап 6А. Проверка банковских источников

## Цель

После завершения сервера, веба, приложений, остальных функций и выпуска базовой версии проверить целевые банки и определить объем финальной интеграции.

Основание: [общий план](../../FINANCE_APP_PLAN.md), разделы 2, 7 и 9.

## Организация работы AI-агентов

Исследователь проверяет API и условия; Android-агент создает прототип; агент проверки проверяет образцы и доказательства. Координатор собирает выводы. Владелец выбирает рынок и банки и предоставляет доступ к устройствам.

Работать по [общему процессу AI-агентов](00_AI_AGENT_WORKFLOW.md). Срок исходного плана относится к команде разработчиков; для AI-реализации оценивать готовность пакетов и внешние зависимости, без автоматического переноса календарной оценки.

## Входные данные

- Страна использования и формат продукта: личное приложение или публичный сервис.
- Список из 3–5 банков для пилота, типы счетов и валюты.
- Доступ к тестовым счетам и устройствам с согласия их владельцев.

Неизвестные значения фиксировать как открытые вопросы. Не считать наличие банка у провайдера доказательством доступа к нужным счетам.

## Пакеты задач для агентов

Каждая строка — пакет для дальнейшего разбиения на карточки по общему процессу. Идентификаторы используются в зависимостях и отчетах; выполнение пока не начато.

| ID | Исполнитель | Вход → результат и область изменений | Зависимости |
|---|---|---|---|
| S1-01 | Координатор | Общий план → описание пилота и список неизвестных в `docs/research/pilot.md` | Этапы 1–5 завершены; выбор рынка и банков — вход от владельца |
| S1-02 | Исследователь | Пилот → матрица покрытия с официальными ссылками, датами и статусом проверки в `docs/research/bank-sources.md` | S1-01; проверять API, цены и условия по актуальным источникам |
| S1-03 | Android | Пилот и обезличенные уведомления → прототип в `android/`, примеры и ожидаемые поля в `tests/fixtures/notifications/` | S1-01; отсутствие реального образца отмечать явно |
| S1-04 | Исследователь | Образцы выписок → описание CSV/OFX и фикстуры в `tests/fixtures/statements/` | S1-01 и получение образцов |
| S1-05 | Проверка и координатор | Результаты пакетов → решение по источникам, ограничения и отчет этапа | S1-02–S1-04; проверить прототип на доступном устройстве |

## Порядок и параллельное выполнение

После определения пилота S1-02, S1-03 и S1-04 выполняются параллельно. Разделить исследовательские документы и наборы примеров между владельцами. При отсутствии реального доступа подготовить прототип и синтетические проверки, оставив проверку банка открытой.

## Проверка результата агентами

Проверить каждую строку матрицы: источник, дата, банк, тип счета, уровень доказательства — документация, sandbox или реальный счет. Зафиксировать фактически проверенные версии Android. Не выдавать предположение парсера за подтвержденный формат банка.

Закрыть этап только после выполнения критериев ниже и записи доказательств в отчет этапа. Оставшиеся внешние зависимости и непроверенные сценарии перечислить явно.

## Входы и действия владельца продукта

Страна, формат продукта, 3–5 банков, обезличенные примеры и действия по включению доступа на устройстве. Без этих данных можно исследовать общую архитектуру, но нельзя завершить подтверждение пилотного покрытия.

## План работ

### 1. Зафиксировать пилот

- Составить список банков, приложений Android, валют и типов операций.
- Определить обязательные сценарии: покупка, доход, перевод, возврат, комиссия, валютная операция.
- Собрать обезличенные примеры уведомлений и выписок; исключить пароли, OTP и персональные реквизиты.

### 2. Проверить банковские API

- Проверить актуальное покрытие GoCardless Bank Account Data, Tink и при необходимости Plaid для выбранного рынка.
- Для каждого кандидата записать доступные счета, историю, остатки, период повторной авторизации и ограничения обновления.
- Уточнить стоимость, условия коммерческого доступа и обработки данных.
- При наличии доступа выполнить тестовое получение счетов и операций. Разделить результаты sandbox и проверки реального банка.

### 3. Создать прототип Android

- Реализовать минимальный `NotificationListenerService` с явным включением доступа пользователем.
- Ограничить обработку выбранными банковскими приложениями.
- Проверить извлечение суммы, валюты, времени, продавца и доступного идентификатора карты.
- Проверить скрытый текст, групповые уведомления, повторные события и работу после перезапуска.
- Зафиксировать ограничения проверенных версий Android, включая доступность содержимого уведомлений.

### 4. Проверить резервные источники

- Получить образцы CSV и OFX целевых банков, описать поля, кодировки и форматы дат.
- Выбрать форматы CSV для MVP; OFX оставить отдельным решением по результатам исследования.
- Оценить SMS как дополнительный канал с отдельной проверкой требований публикации. Не делать его обязательной зависимостью MVP.

### 5. Принять решение по источникам

- Для каждого банка указать основной источник, резервный источник и ограничения полноты данных.
- Определить банки, для которых создаются первые парсеры.
- Выбрать одного API-провайдера для следующей интеграции либо зафиксировать причину отсрочки.

## Результаты

- Матрица «банк → API → уведомления → выписка → ограничения» с датой проверки.
- Android-прототип и обезличенные примеры для будущих тестов парсеров.
- Решение по провайдеру, стоимости и внешним зависимостям.
- Список открытых вопросов с ответственными и условиями закрытия.

## Критерии завершения

- Для каждого пилотного банка есть проверенный способ получения операций либо явно отмечено отсутствие поддержки.
- Ограничения уведомлений и полноты истории описаны.
- Есть проверенный резервный путь первоначального заполнения данных.
- Координатор может определить объем проектирования и импорта без предположения об универсальном банковском доступе.

## Риски и зависимости

Коммерческий доступ к API может задержаться. В этом случае продолжать проектирование MVP на уведомлениях и CSV, а интеграцию API вести как внешнюю зависимость. Уведомления не считать полной банковской историей.

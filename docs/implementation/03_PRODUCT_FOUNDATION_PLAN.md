# Этап 1. Серверная часть и веб-интерфейс

## Цель

Получить работающий ручной учет финансов в вебе с Go API и PostgreSQL. Приложения реализуются после завершения этого этапа.

Основание: [общий план](../../FINANCE_APP_PLAN.md), разделы 1, 3–6 и 7.

## Организация работы AI-агентов

Агенты Go и веба реализуют свои компоненты; агент проверки проверяет финансовые инварианты и доступ. Координатор интегрирует сквозные сценарии по общему контракту.

Работать по [общему процессу AI-агентов](00_AI_AGENT_WORKFLOW.md). Срок исходного плана относится к команде разработчиков; для AI-реализации оценивать готовность пакетов и внешние зависимости, без автоматического переноса календарной оценки.

## Зависимости

Нужны [результаты проектирования](02_DESIGN_PLAN.md): модель данных, макеты, API и правила конфликтов.

## Порядок и параллельное выполнение

После S3-01 веб-задачи выполняются параллельно серверным на контрактных ответах. Android-пакет S3-05 перенесен в план приложений. Разбить S3-02–S3-04 на карточки по модулям; порядок миграций контролирует один владелец. До расширения функциональности интегрировать один сценарий: ручной расход в вебе → сервер → корректный остаток в вебе.

## Проверка результата агентами

Запустить сборки сервера и веба, серверные тесты с тестовой PostgreSQL и миграции. Проверить атомарность движений, точность денег, доступ другого пользователя и повторную отправку. Проверить создание и редактирование операций через веб, ошибки API и конфликт версий.

Закрыть этап только после выполнения критериев ниже и записи доказательств в отчет этапа. Оставшиеся внешние зависимости и непроверенные сценарии перечислить явно.

## Входы и действия владельца продукта

Ограничения тестового окружения сервера и веба. Если инструмент отсутствует, агент передает точную незапущенную проверку; сквозная приемка остается открытой.

## План работ

### 1. Подготовить основу разработки

- Создать модульный монолит Go с процессами API и worker из общей кодовой базы.
- Настроить Docker Compose: веб, PostgreSQL с постоянным volume, API, worker и одноразовые миграции; отдельное test-окружение, общий HTTPS origin и проверки сборки.
- Создать веб-приложение на React и TypeScript.
- Подготовить тестовое окружение, конфигурацию секретов и безопасный сбор ошибок.

### 2. Реализовать пользователей и доступ

- Регистрация, вход, выход, обновление и отзыв сессий.
- Управление устройствами и создание личного пространства финансов.
- Проверка прав на каждом запросе к пространству, счетам и операциям.

### 3. Реализовать финансовое ядро

- Счета разных типов и валют, начальный остаток и архивирование.
- Расходы, доходы, переводы, возвраты, комиссии и разделение по категориям.
- Изменение остатков только через движения, включая явную корректировку.
- Атомарная запись операции и движений в PostgreSQL.
- Дерево категорий, теги, поиск и фильтрация операций.
- Сохранение точности сумм и пользовательских правок.

### 4. Подготовить серверный API синхронизации

- Безопасно обрабатывать повторные запросы с уникальным ключом действия.
- Проверять версии и возвращать изменения по курсору, включая удаления.
- Описать конфликты и восстановление устаревшего курсора в контракте.
- Реализацию Room, outbox и WorkManager выполнить на этапе приложений.

### 5. Собрать основные интерфейсы

- В вебе: те же базовые сценарии, фильтры и массовое редактирование с проверкой прав и версий.
- Показать ошибки валидации, отсутствие связи и конфликтные записи.

## Результаты

- Запускаемые API, worker и веб.
- Миграции PostgreSQL и реализация финансового ядра.
- Рабочий веб с сервером и проверенный серверный контракт синхронизации.
- Автоматические проверки финансовых инвариантов, доступа и повторной отправки.

## Критерии завершения

- Пользователь создает счет и операцию в вебе, затем видит корректный остаток после перезагрузки.
- Повторная отправка не создает вторую операцию или движение.
- Переводы не увеличивают доходы и расходы; валютные суммы сохраняются точно.
- Конкурирующие финансовые правки не теряются молча.
- Запросы к чужим счетам и операциям отклоняются.

## Риски и зависимости

Синхронизация и финансовая модель — основные риски этапа. Сначала проверить один сквозной сценарий от веба до PostgreSQL, затем расширять типы операций. Поддержку импорта готовить через согласованный интерфейс источников.

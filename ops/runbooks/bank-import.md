# Импорт подготовленного банковского плана

`backend/cmd/import-ledger` — операторская утилита для проверенного JSON-плана,
не HTTP endpoint и не автоматический распознаватель банковских CSV.

До импорта создать custom-format backup через `ops/backup.sh prod`, проверить
SHA256 и восстановление в отдельную тестовую БД. Исходные выписки, план,
результаты сверки и дампы содержат личные данные; хранить их вне Git в каталоге
с правами 0700, файлы — 0600.

План содержит `workspace`, `actor` (владелец пространства), `generation`,
`expected_head` (проверенный `sync_heads.last_sequence`) и `operations`.
Каждая операция содержит стабильный уникальный `action_id`, `type` и `payload`.
Поддерживаются `basic`, `transfer`, `refund`, `adjustment`, `account`; payload
проходит соответствующий строгий декодер ledger. Денежные суммы — строки целых
минимальных единиц, моменты — UTC RFC3339 с `Z`.

С подключением через защищенную переменную `DATABASE_URL`:

```sh
go run ./cmd/import-ledger < /private/reviewed-plan.json
go run ./cmd/import-ledger -apply < /private/reviewed-plan.json
```

Первая команда выполняет весь план и откатывает изменения. Вторая атомарно
сохраняет весь план. Сначала проверить оба режима и повторный `-apply` на
восстановленной копии. Применять в рабочей БД только после сверки новых движений,
сохранности прежних операций и наличия квитанций, audit и sync-групп.

Каждый шаг использует обычную команду учета и отдельную sync-группу. Ошибка
любого шага откатывает весь план, включая квитанции. Изменение пространства
после подготовки плана останавливает импорт. Повтор того же успешно примененного
плана возвращает сохраненные квитанции и не добавляет движений. Не менять
идентификаторы и payload уже примененного плана.

Перед подготовкой плана исключить дубли между выписками, сопоставить ранее
введенные операции и определить реальные счета. Одного совпадения суммы
недостаточно. Отмененные операции не импортировать; незавершенные не превращать
в проведенные. Неизвестную вторую сторону и курс перевода не выдумывать:
допустимо сохранить подтвержденное signed движение как историческую adjustment
с явной причиной и исходной строкой в заметке для последующей сверки. Такая
запись не является корректировкой остатка до произвольного целевого значения
и не входит в отчеты доходов/расходов. Начальные остатки самостоятельно не менять.

Если владелец объединяет депозитный и карточный/текущий счета одной валюты в
существующий счет приложения, пополнения и выплаты вклада внутри этой группы
пропускать как внутренние движения. Проценты сохранять как доход на общем счете.
Это правило применяется к подтвержденному объединению FFin EUR и FFin RUB.
Выплату вклада нельзя подменять расходом по карте: если выписка содержит только
движения депозита, для учета покупок нужна отдельная история карточных операций.
Каждую пропущенную исходную строку сохранять в защищенном отчете сверки с причиной
и счетом назначения; повторно применять ранее импортированные планы не нужно.

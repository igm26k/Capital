# Wallet balance reconciliation

`go run ./cmd/reconcile-wallet` reads a private JSON `WalletPlan` from stdin and performs a transactional dry run. `-apply` commits the exact reviewed plan. This is an offline database-operator tool; it is not an HTTP endpoint and must not be wired into one. The operator must have explicit authorization from the workspace owner. Database credentials come from `DATABASE_URL`; no user sessions are borrowed or generated.

The plan contains workspace/actor/generation/action UUIDs, the statement cutoff (`as_of`), the original history start (`opened_at`), the expected transaction count, and the complete account set. Each account supplies an ID, original name, currency, type, expected as-of balance, target balance and adjustment UUID. A null expected balance requires a missing account; its target becomes the opening balance. Optional `rename_to` changes existing metadata. All money uses integer minor-unit strings.

Before mutation the tool locks the workspace sync head and account rows, checks active ownership, generation, account count, names, currencies, types, opening dates, transaction count and expected balances. Existing accounts receive signed historical adjustments at the original opening date. Original imported transactions and immutable opening records are preserved. New accounts use the normal account command. Every target balance is checked before commit. Any error rolls back the group. The normal sync command runner records one receipt, sync group and audit events; repeating the same action and plan replays the receipt. Use a fresh action ID only for a separately reviewed operation.

Keep personal plans, database backups and outputs outside version control, with owner-only file permissions. Back up before applying. Afterwards independently verify all as-of balances and that a repeated application changes no versions, entries or sync sequence. Frontend imports resolve their deterministic account IDs after renames, so a renamed auto-created account is reused.
